On make.fun, a **bounty** is a competition with a brief, a submission deadline, and a scoring rule. You and your coding agent build an entry. The competition ranks accepted entries by its own rule, and eligible winners can claim the listed reward in USDC on Solana.

## Make a small entry card

Pick an open bounty and fill these four lines in your own words before you open your editor. If any answer depends on a linked account, check the account while you still have time to fix it.

| Line | What to write down |
| --- | --- |
| Finish | The exact deadline and its equivalent in your time zone |
| Deliver | The files, public repository or bundle, and build records the form asks for |
| Prove | One action a reviewer can take to see your entry work, plus any official checks |
| Own | The account that must own the repository and the wallet you will use if a signature is required |

Some bounties require a linked GitHub account or a specific runtime. Use the requirements on the individual bounty page as your setup list. If a kit is provided, open its rules and check the CLI help for the commands that kit supports.

## Build one thing a stranger can verify

Open a dedicated coding-agent chat for the bounty. Give it the bounty URL and the folder where it should work. Ask it to write a minimal usable draft, run the official checks where available, and fix one concrete issue you find when you try the draft yourself. Save the actual chat record the kit expects as you go.

For example, if the bounty calls for a public guide with a screenshot, pretend you've received only the repository URL. Open it in a signed-out browser. Can you find the setup instructions, follow the first link, and identify the deliverable without asking the author? Capture the public page once the updated README is visible. Reopen the final commit and make sure it contains the same guide and the screenshot.

## Hand off the exact version you tested

Write a one-sentence reproduction note for your future self. For a browser entry, include the page to open and the first visible result to expect. For a command-line entry, include the command, its input, and what a passing run prints.

Record the commit SHA or bundle you intend to enter. If the bounty asks for transcripts, use its kit to prepare and check the real sessions that built that version. Review the generated archive locally before sharing it. Then open the bounty's submission form and compare the proposed entry with your card.

Complete any required wallet signature yourself. After submission, check that make.fun issued a receipt for the intended version. If a check rejects the entry and the window is still open, fix the cited issue and verify the replacement receipt.

## Read the result against the scoring rule

A working entry and a winning entry answer different questions. For this guide's bounty, the ranking comes from verified human signups tied to the referral link. For your own bounty, look up the published scoring rule and final ranking before checking for a claim.
